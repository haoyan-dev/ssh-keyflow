## Source-hosted one-line installers

- `install.sh` (POSIX sh on Linux/macOS) and `install.ps1` (Windows PowerShell 5.1 or PowerShell 7) are served from `main` through `raw.githubusercontent.com/haoyan-dev/ssh-keyflow/main/`. They consume the existing Portable release archives, including v0.2.0, without changing release assets. Entry points: `curl -fsSL <install.sh URL> | sh` and `irm <install.ps1 URL> | iex`. Source delivery follows `main`; version selection controls which Portable release is downloaded.
- Default repository `haoyan-dev/ssh-keyflow`, overridable with `--repository` / `-Repository` or `SSH_KEYFLOW_REPOSITORY`. Latest resolution requires a stable, nondraft, nonprerelease version; an explicit `--version` / `-Version` may select a prerelease. The same six OS/CPU targets as the Portable archives are supported.
- The installer downloads the archive and SHA256SUMS, requires exactly one matching checksum, and rejects unexpected members, links and nonregular entries before installing. Both the executable and `THIRD_PARTY_NOTICES.txt` are installed.
- Default locations: `$HOME/.local/bin` and `$env:LOCALAPPDATA/Programs/ssh-keyflow`. The v0.1.0 ownership formats are retained, with notice ownership added (`notices-hash` in the POSIX receipt directory, `noticesHash` in the Windows receipt JSON). An intact legacy receipt without notices upgrades directly. Unowned, changed or missing owned files stop installation/removal. A failed replacement or receipt write restores the previous executable, notices and ownership hashes.
- PATH changes require terminal consent or an explicit `--add-to-path` / `-AddToPath`. Piped source is never read as an answer. Noninteractive execution without consent leaves profiles unchanged and prints the full launch path and a manual PATH command. PowerShell treats a host refusal to prompt under `-NonInteractive` as declined consent. PowerShell argument parsing and installation run in a child scope (including under `Invoke-Expression`) to preserve caller variables, strict mode and error preferences.
- Profile changes use same-filesystem staging and atomic replacement, preserving existing metadata and recovery copies until ownership is recorded. A PATH setup failure restores the profile and the previous executable, notices and receipt. PATH stanzas are idempotent and byte-owned; uninstall removes only the exact, unique owned stanza, the executable, notices and receipt. Existing v0.1.0 stanzas stay owned across upgrades.
- SSH keys, state, SSH configurations and remote registrations are never modified. The application must be shut down before update/removal; PATH profile persistence takes effect in a new shell.
- Isolated tests use loopback HTTP through `SSH_KEYFLOW_RELEASE_URL` and `SSH_KEYFLOW_API_URL`; normal defaults use HTTPS GitHub endpoints.

Authoritative section: [Source-hosted one-line installers](../../application-contract.md#source-hosted-one-line-installers).

## Portable release

- `scripts/package_release.py --version <tag> [--output <empty-directory>]` builds Windows/Linux/macOS amd64/arm64 with CGO disabled, VCS stamping disabled, trimpath and injected `main.version`. Existing nonempty output is refused. `--binaries <directory>` instead packages six prebuilt OS_ARCH binaries for artifact tests. Assets are staged before being published to the output directory.
- The release contains exactly six archives and `SHA256SUMS` (seven assets), with no installer. Windows archives are zip, Linux/macOS archives tar.gz. Each contains only its platform executable and `THIRD_PARTY_NOTICES.txt`. Unix executable mode 0755, notice mode 0644, tar uid/gid zero. The manifest lists six unique archive basenames with SHA256, two spaces and LF. Notices keep dependency license/copyright text, including platform-specific modules and Unicode data; collection evidence is in `docs/third-party-notices.md`.
- Portable means a freely placed executable. Storage stays at `<Home>/.ssh/ssh-keyflow`; moving, replacing or removing the executable neither migrates data nor changes SSH keys, state, config, remote registrations, PATH, profiles or installer receipts. End users need the OS OpenSSH, not Go. They exit the app before manual replacement/removal and keep the notice document when redistributing the binary.
- Old v0.1.0 installers require a single archive member and therefore reject the new archives; use the new source-hosted installer for intact v0.1.0 installations. Manual binary replacement invalidates the old ownership digest, so updates/removal may be rejected. The README documents manual maintenance and optional manual cleanup of the exact owned PATH stanza; changed receipts/profiles are not repaired automatically.
- CI runs Go and Portable artifact tests on three OSes plus actual six-target cross-builds. The release workflow uploads the seven staged assets after CI; the implementation itself does not tag, push or publish. Fixture artifact tests and cross-builds do not establish native runtime behavior on every target.

Authoritative section: [Portable release](../../application-contract.md#portable-release).

## Current feature scope (v0.5.0 and later)

- SSH KeyFlow is limited to local key management and copy-and-paste connection setup support. This contract replaces the old descriptions of automatic registration/unregistration, SSH connection checks, config editing, key deletion, the numbered menu, Tasks and recursive config discovery. This is an intentional incompatible change introduced in v0.5.0 and does not apply retroactively to v0.4.0 or earlier binaries. Distribution, installers and the publishing procedure are kept.
- Deploying and removing public keys is manual work for the user. The app does not run or generate SSH processes, remote authentication or probes, or scripts for installing/starting servers or changing firewalls. Per ADR 0002, it does generate public key deployment and local config append scripts that the user pastes into and runs on the target terminal.
- New keys, associations and guides are unverified with respect to registration and connection, and there is no operation for recording manual success. Past success records are kept as history and are not interpreted as current connectability.

## CLI

The entry point is `cli.Run(ctx, args, cli.Options{Home, Version, Input, Output, Error, Runner, RunTUI}) int`, and `cmd/ssh-keyflow` returns its exit code. Home resolution is deferred until an operation needs it.

| Command | Input |
| --- | --- |
| `keys list` | Optional `--json`. Shows keys and unfinished local creation IDs |
| `keys create` | Required `--name`. Creates an Ed25519 key |
| `keys import` | Required `--name`, `--public`. Optional `--private` verifies the key pair; without it the key is public-key-only |
| `keys public` | Required `--key`. Shows the public key algorithm and blob, without the file's comment |
| `keys remove` | Required `--key`. Removes the key and all its associations from management; key files are kept |
| `hosts list` | Optional `--json`. Shows destinations, new associations and host key pin status |
| `hosts add` | Required `--alias`, `--hostname`, `--user`, `--os`, and `--key` for an existing key. `--port` defaults to 22. Windows requires `--windows-account standard\|administrator` |
| `hosts associate` | Required `--host`, `--key`. Saves a local association |
| `hosts dissociate` | Required `--host`, `--key`. Removes only the specified existing association |
| `hosts remove` | Required `--host`. Removes the destination and all its associations from management |
| `hosts guide` | Required `--host`, `--key`. Optional `--local-os`, `--remote-os`, `--windows-account`, `--identity-file`. Read-only deployment, removal and connection setup guide |
| `hosts pin` | Required `--host`. Optional `--file`, `--yes`, `--replace`. Pins host public keys displayed on the destination (ADR 0006) |
| `hosts unpin` | Required `--host`. Removes the pinned host public keys |
| `resume` | Required `--id`. Unfinished local Creation IDs only |
| `tui` | No extra arguments. Requires a real terminal for both input and output |

- `--os` is explicitly `linux` / `macos` / `windows`. A destination resolves by fixed ID or case-insensitive alias; a key by fixed ID or unique exact managed name. Ambiguous or missing targets are rejected. Duplicate aliases among managed destinations are rejected, but aliases inside the SSH config are not searched. Adding a destination requires an existing key and never creates a new key at the same time.
- `register`, `unregister`, `registrations list`, `keys delete`, `--new-key`, `--auth`, `--identity` and `--configure` are not provided. `resume` does not run legacy remote or deletion IDs and asks for manual review.
- Per ADR 0004, `remove-key` / `remove-host` / `dissociate` are shared-backend Operations using a real terminal and exact `yes` confirmation, re-resolution of the target under the lock, atomic save and the previous-state backup. Removing a key or destination removes all its associations; dissociation removes only the specified pair. A nonexistent pair is an argument error. No key file verification or external process is needed, so management data for missing keys can be cleaned up. A key with an unfinished legacy key deletion requires manual review and cannot be removed from management.
- Removed keys and destinations are kept in the optional v2 arrays `removed_keys` / `removed_hosts`. References from legacy registrations, creation results, onboardings and config history are validated against archived IDs too, and history is never rewritten. Current associations may reference only managed keys and destinations. Archived fingerprints, paths and aliases may be reused; re-import and re-adding a destination create new IDs. Lists, public key output, guides and selection candidates exclude removed records. Key files, SSH configuration and remote registrations are not changed, and removal does not mean access is revoked. Old binaries reject state containing the archive arrays, so downgrades must use state saved beforehand. In the TUI, `d` in a list/details removes, and `u` dissociates with only the selected item's existing associations as candidates, handing off to the real-terminal confirmation.
- Changing operations require real-terminal input before storage initialization or any process execution, and pass an explicit Request and confirmation function to the shared `app.Run`. Only an exact `yes` (surrounding whitespace trimmed) approves. `ReadConfirmation` reads one line byte by byte and does not read ahead into the following native passphrase input. There are no flags for secrets or unconditional approval. The only exception is `hosts pin --yes`, which skips confirmation only when no different key is pinned, and never approves a replacement.
- Exit codes: 0 success, 1 execution failure or cancellation, 2 argument/usage error. Ambiguous or missing targets are argument errors, and the command's usage is written to stderr; runtime diagnostics carry no usage. `--help` and `--version` do not resolve Home, check dependency commands or save anything. The version output is `SSH KeyFlow <version>`.
- With no arguments, if either input or output is not a terminal, help is printed and the exit code is 0; if both are real terminals, the TUI opens. An explicit `tui` that violates the terminal requirement returns 2. Lists, public key output and guides can be redirected and do not probe writability or SSH commands.
- List output is a table by default. JSON is a single object ending with a newline: `keys list` returns `keys` / `creations`; `hosts list` returns `hosts` / `associations` / `host_key_pins`. `host_key_pins` maps managed destination IDs to `[{type, fingerprint}]`, excludes pins of removed destinations, and is omitted with a reason on stderr if the pin file cannot be read. The table's `HOST KEYS` column shows `pinned (N)` / `not pinned` / `unknown`. Arrays are empty arrays, not null, and field names match the storage schema. Items needing review go only to stderr, and verifiable state records remain readable. Invalid state returns 1, prints no JSON and keeps the original file. Public key and guide output write copyable text to stdout. An output failure is an execution failure.

## Shared backend and manual guide

- `app.Request` Operations are `list` / `create` / `import` / `add` / `associate` / `dissociate` / `remove-key` / `remove-host` / `guide` / `public` / `resume` / `pin-host` / `unpin-host`. `app.Run` requires an explicit Request and never starts the old numbered menu. Change targets are re-resolved and re-validated under the lock.
- `app.Snapshot(Options)` returns `View{State, Review}` without initializing storage, probing dependency commands or changing legacy records. `app.PublicKey(home, keyRef)` and `app.Guide(home, hostRef, keyRef)` verify the target key's identity and return text. `app.PrepareGuide` returns `SetupGuide{Text, Steps}` after the same verification; the TUI uses each `GuideStep`'s `Title` / `Instructions` / `Script`. Showing a guide neither assumes a saved association nor saves a new one.
- `app.PrepareGuideWithOptions(home, hostRef, keyRef, GuideOptions)` additionally accepts guide-only `LocalOS` / `RemoteOS` / `WindowsAccount` / `IdentityFile`; `app.Request.GuideOptions` passes the same choices to the shared backend. OS values are `linux` / `macos` / `windows`; defaults are the OS running the app and the saved destination OS and account. Changing to a different destination OS does not carry over the original Windows account type. Windows requires standard / administrator, and an account for a non-Windows destination is rejected. The TUI shows these defaults in a form after the destination and key are chosen; choices are not saved. For a managed private key, only the format header is read; if it has a passphrase or cannot be determined, `AddKeysToAgent yes` and a local-OS ssh-agent step (between the config append and the connection) are added. With `IdentityFile` given, the key is not inspected and is treated as undeterminable (ADR 0005).
- The guide contains the public key algorithm and blob, fingerprint, deployment target, manual removal instructions and local file paths. The first step is a public key deployment script for the selected destination OS and account type: POSIX shell for Linux/macOS, PowerShell for Windows. It keeps existing keys, does not append if the same public key is present, separates the append from an existing last line without a newline, and rejects symbolic links and reparse points. It checks the login user name (POSIX), the user name (Windows standard account) or an elevated terminal (Windows administrator account). Targets for the standard OpenSSH configuration:

| Destination | Target and checks |
| --- | --- |
| Linux / macOS | The login user's `~/.ssh/authorized_keys`. Keeps existing lines; user-owned `.ssh` is 700 and the file 600 |
| Windows standard account | `%USERPROFILE%\.ssh\authorized_keys`. Keeps existing lines; write permission limited to the user, SYSTEM and Administrators |
| Windows administrator account | `%ProgramData%\ssh\administrators_authorized_keys`. Shared across administrator logins, so other keys are kept and the SYSTEM/Administrators ACL is checked |

- With a custom configuration, the user checks the actual `AuthorizedKeysFile` / `Match`. The SSH server and network are assumed to be available beforehand. For removal, keep another working means of access and manually remove only the matching public key line from the same file; the result is not verified.
- The second step is a script that appends a Host snippet with client `HostName` / `User` / `Port` / `IdentityFile` / `IdentitiesOnly yes` to `~/.ssh/config`, using the private key path (or the saved public key path for a public-key-only key), in PowerShell for a Windows local OS and POSIX shell for Linux/macOS. With a local OS different from the one running the app, the in-terminal path of the matching private key is required via IdentityFile: an absolute path for that OS or ~/path; control characters, relative paths and paths for another OS are rejected. The file at that path is not read, and key transfer, path conversion and matching are not guaranteed. Identity verification of the managed source file is kept, and a public-key-only key is not turned into a key pair by an IdentityFile option. The script keeps existing content and stops if the same explicit alias exists, including in grouped Host lines. Include, wildcard and Match resolution and precedence are not guaranteed. In PowerShell, an existing file must be UTF-8; UTF-16 and invalid UTF-8 are rejected before appending. Windows public key deployment limits the DACL of the `.ssh` directory and key file to the user, SYSTEM and Administrators for a standard account, and of the shared file only to SYSTEM and Administrators for an administrator account, keeping owner and audit information and using the .NET ACL APIs of Windows PowerShell 5.1 / PowerShell 7.
- The third step is the `ssh 別名` connection command used on the local terminal after the first two steps. It is common to POSIX shell and PowerShell and does not repeat the private key path as a command argument. Considering OpenSSH's own expansion, `%` is escaped in IdentityFile. Paths containing `${...}` cannot be guaranteed to be referenced literally, so the public key deployment guidance is kept and the config append and connection steps are omitted with the reason shown. For a public-key-only key, the public key file is used as `IdentityFile` so that OpenSSH uses only the matching key from the SSH agent (such as a FIDO key), and the guide states that the matching private key must be loaded into the agent; no `AddKeysToAgent` or ssh-agent step is added. With a different local OS, `--identity-file` is requested, and without it only the deployment step is shown. The app runs none of the scripts or commands.
- The app itself never edits, regenerates or deletes the normal `~/.ssh/config`, the past dedicated config, Include files or backups. The normal config is appended only when the user runs the copied append script. Recursive discovery and wildcard/Include precedence analysis are not provided; the user checks the paste target and duplicates/precedence with existing Host entries. An existing Include that enables the past dedicated config also stays as it is.

## Host key pinning

- Per ADR 0006, the destination's host public keys are pinned in the app-owned `<Home>/.ssh/ssh-keyflow/known_hosts`. On the destination's own terminal the user runs `cat /etc/ssh/ssh_host_*_key.pub` (POSIX) or, in a PowerShell opened as administrator, `Get-Content "$env:ProgramData\ssh\ssh_host_*_key.pub"` (Windows), and pastes the output. The app opens no network connection and does not edit `~/.ssh/known_hosts`, SSH config or `sshd_config`.
- `hosts pin` shows the display command and reads pasted input until an empty line in a real terminal, reads standard input when not a terminal, or reads `--file`. Input is limited to 64 KiB and 16 keys. Only lines of the form `<type> <base64> [comment]` with canonical base64 for `ssh-ed25519` / `ecdsa-sha2-nistp256` / `ecdsa-sha2-nistp384` / `ecdsa-sha2-nistp521` / `ssh-rsa`, whose blob algorithm matches, are accepted. Comments are discarded; other lines are shown as ignored and do not block valid keys. Each key's type and SHA256 fingerprint are shown, and an exact `yes` saves them. Re-pinning the same key set writes nothing. Non-terminal input requires `--yes`, which skips confirmation only when no different key is pinned. If different keys are pinned, old and new fingerprints and a warning are shown, and `--replace` plus `yes` in a real terminal are required.
- `hosts unpin` removes only that destination's lines after confirmation in a real terminal. Both commands work only on managed destinations. Removing a destination keeps its pins, so the removal confirmation advises running `hosts unpin` first.
- The pin file has one key per line, `ssh-keyflow-<host-id> <type> <base64>`, LF-terminated. Writes use the same lock, atomic replacement, symbolic link rejection and permission checks as the state, and preserve the order and content of other destinations' lines. Reads are strict: a file with invalid lines, CRLF, tabs, duplicates, comments or markers stops pinning and unpinning and is never repaired automatically. The state schema does not change.
- The guide reads the pin status when generated. Only when the local OS is the same as the one running the app: if not pinned, the destination's "ホスト鍵の表示" (display host keys) step and the local "ホスト鍵の固定" (pin host keys) step (`ssh-keyflow hosts pin --host <id>`) are added after the deployment step; if pinned, `HostKeyAlias ssh-keyflow-<host-id>`, a quoted slash-separated absolute `UserKnownHostsFile` path and `StrictHostKeyChecking yes` are added after `IdentitiesOnly yes` in the Host snippet. The path uses the same escaping as IdentityFile, and no lines are generated if it contains control characters or `${`. If the pin file cannot be read, `Host keys: unknown` is shown and no pinning lines or steps are added. The snippet for an unpinned destination is unchanged. For an existing Host, the user adds the three lines manually.

## TUI

- `tui.Run(ctx, app.Options)` is the CLI's TUI entry point, centered on two screens, Keys / Destinations. It provides key creation and import, adding destinations with existing keys, association and dissociation, removal from management, and showing/copying public keys and guides. New keys are created independently. The old Registrations / Tasks, remote authentication and config editing forms, and key file deletion are not provided.
- Keys: Tab switches screens, c/i create/import a key, a adds a destination, l associates, u dissociates an existing association, d removes from management, p/g show the public key/guide, s resumes the selected local creation. `t` / `T` pin / unpin the selected destination's host keys, handing off to the native terminal for paste and `yes` input (pinning specifies Replace and shows old and new fingerprints if different keys exist). Destination details show `Host keys: pinned (N)` / `not pinned` / `unknown`. y requests an OSC52 copy of the displayed text; if the terminal does not support it, the user is advised to use the CLI public key/guide output. Public keys stay on one line, and TUI wrapping is not copied as line breaks. v shows legacy records read-only in technical details. Minimum terminal size is 32 columns × 12 rows. The in-app help is authoritative for key details.
- The guide is shown from the first step and switched with ← / → or `b` / `n`. `y` copies only the selected `Script`, without explanatory text or scripts for other terminals. Each step states local / destination, OS, terminal, and the required account and permissions. The selected step is kept when returning from Help. On F5 reload, scripts (including those in history) are invalidated, and switching steps never restores a stale copy.
- The TUI uses the same validation and save processing as the CLI and never starts execution from reading or showing a guide. Changes are accompanied by confirmation of the target and impact. When needed, the terminal is handed to the native `ssh-keygen`, and passphrases are never held in the TUI or the state. Failure, interruption and cancellation are never shown as success, and saved progress is not treated as rolled back.

## Storage schema and compatibility

- Storage is `<Home>/.ssh/ssh-keyflow`, using `state.json`, `keys/` for generated keys, the rolling `state.json.bak`, a temporary `state.lock`, and the host key pin file `known_hosts` created on the first pin. With no state, an empty v2 state is returned and no file is created on read.
- v1 and v2 are read. Reading v1 does not change its contents, version or backup; it becomes v2 on the first successful state save. v2 `associations` are `{host_id, key_id}` pairs referencing valid keys and destinations, with no duplicate pairs. Legacy `registrations` / `history` are not converted into associations, and their registration/connection status is not changed.

| Record | Saved fields |
| --- | --- |
| Key | `id`, `name`, `fingerprint`, `public_path`, optional `private_path` / `private_sha256`, `connection_check`, `origin`, `imported_at`, optional `created_at` |
| Host | `id`, `alias`, `hostname`, `user`, `port`, `os`, optional `windows_account` / legacy `config_key_id` |
| Association | `host_id`, `key_id` |
| Creation | `id`, `key_id`, `name`, `private_path`, `public_path`, `created_at`, `stage`, optional `private_sha256` / `fingerprint` |

- Required arrays are `keys` / `hosts` / `registrations`. Optional `creations` / `associations` / `removed_keys` / `removed_hosts` and legacy `onboardings` / `history` / `configs` / `config_edits` / `deletions` / `deleted_keys` are preserved. Past fixed IDs, registration history, config digests, interrupted intents and deleted key information and their references are kept and are not rewritten as success or completion of new operations. There is no command for browsing legacy history, but the saved data remains. v2 saves reformat the JSON, so preserving past record values is distinct from leaving the state file's bytes unchanged.
- Key IDs are fixed random `key-<128-bit hex>`, fingerprints are the SHA256 form of the OpenSSH public blob, and paths are absolute. Import saves `origin: imported` and a nonzero UTC RFC3339Nano `imported_at`; creation saves `origin: created` and `created_at`. The private key digest detects replacement without asking for a passphrase and does not store private key contents. New keys have `connection_check` `unverified`, and associations have no success-status field.
- Invalid or trailing JSON, duplicate or unknown fields, unsupported versions, missing required arrays, invalid metadata, duplicate IDs/aliases/fingerprints/paths, and contradictory or orphaned references are rejected on load, without automatic restore or overwrite. Unfinished records of legacy remote operations and config editing are read-only and never resumed automatically. An unfinished legacy deletion makes only the affected key unusable and requires manual review; that record alone does not block operations on other keys.
- `state.json.bak` is the exact bytes of the validated `state.json` immediately before a save. It is updated on every save, so even within the same operation after migration it can be replaced by v2. It is not a permanent v1 migration backup. **Users who may need to downgrade must exit the app and save the v1 state separately before the first changing operation on v0.5.0 or later.** Older apps cannot read v2, so manual restoration from the saved v1 state and review of data added after migration are required. No migration copy is made on read, and existing keys, config, Include files and backups are not rewritten as part of migration.

## Local key safety conditions and storage

- Creation uses the native `ssh-keygen -t ed25519` and allows an empty passphrase. The target is `keys/id_ed25519_<安全化した管理名>_<UTC時刻>` (sanitized managed name and UTC time) with a numeric suffix on collision. Both paths and saved reservations are checked, and checked again after confirmation. Existing files are never overwritten or adopted automatically.
- Before any side effect, the creation intent, fixed ID and paths are saved, and `planned` / `pending` / `complete` progress is maintained. Resume uses the same paths: with no files it generates; with only a private key it derives the missing public key with the native `ssh-keygen -y` and creates it exclusively; with a pair it verifies without regenerating. Public-key-only, empty or nonregular files, changed fixed fingerprints/digests, or disappearance of observed files stop for review. Partial files are never deleted automatically, and no other key pair is newly created while a creation is unfinished.
- Import also verifies the specified public key with `ssh-keygen -l -E sha256`, and with a private key requires it to match the public key fingerprint from `ssh-keygen -y`. Original files are not moved or rewritten. Fingerprints and the private key digest are rechecked before saving, and missing or replaced files are not treated as success. There is no API for deleting local files or automatic cleanup.
- All changes are protected by the exclusive `state.lock` through `state.WithLock`, held during confirmation, creation and saving. LockedStore is not used outside the lock, and locks are not nested. Existing locks are never deleted automatically, and writability is checked only when changing. After validation, state is written and synced to a temporary file in the same directory, the previous valid state is atomically saved to `.bak`, and then `state.json` is replaced. If the backup fails, the current state is not replaced. Users must not edit target key paths concurrently during an operation.

## Verification and publishing

- The README's Go tests and vet, the Portable / installer tests and the six-target builds apply. Tests use a temporary home and substitute processes and do not change the real user's SSH data, PATH, profiles or destinations. Covered checks include unchanged v1 reads, v2 migration with an exact previous-state backup, preserved legacy history, deletion blocking only for affected keys, read-only behavior of reads, and key creation resume with identity verification.
- Results, target commits, environments and unverified scope are recorded in `docs/verification.md`. Past automatic registration/unregistration test records are history, not the current contract or verification of the new implementation. Cross-builds are distinct from evidence of running the TUI and native key creation on each OS. Showing a guide does not verify actual destination settings, registration, removal or connection success.
- Publishing uses an annotated `vMAJOR.MINOR.PATCH` tag on a commit merged into and verified on main. [Tags and releases in AGENTS.md](../../../AGENTS.md#tags-and-releases) is authoritative for the steps, completion criteria and approval scope from merging the preparation PR, verifying the final candidate, creating and publishing the tag, to merging the post-release record PR. The preparation record references the verified source commit; the final tag's commit is kept in the tag, release information and post-release record. Even if main moves ahead of the tag with audit documents, the published tag keeps pointing at its build source. Pushing a `v*` tag starts automatic publication after CI. Prereleases are never made latest, and the stable latest advances to newer stable versions. Published tags and binary assets are immutable; fixes ship as new versions. After publishing, distributions, checksums, internal version, tag and source commit are checked to match. Development builds continue to show `dev`.
