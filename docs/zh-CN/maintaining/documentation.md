# 文档维护

简体中文 · [English](../../en/maintaining/documentation.md) · [日本語](../../maintaining/documentation.md)

[文档索引](../README.md) · [参与贡献](../../../CONTRIBUTING.zh-CN.md)

文档以可在 GitHub 上阅读的 Markdown 形式，与源代码在同一 PR 中管理。需支持的语言为简体中文（`zh-CN`）、英语（`en`）和日语（`ja`）。命令、标识符和界面标签使用实现中的写法。

## 多语言支持要求

README、文档索引、教程、操作与问题处理指南、参与贡献、文档维护与发布指南均以 3 种语言提供。公开规格的说明也应能从各语言访问，契约和术语的正本则统一管理。过去的研究、工单、ADR 和验证记录无需追溯翻译。

- 在 README 和各页面中放置 `简体中文` / `English` / `日本語` 的语言链接，以便跳转到内容相同的页面。对于未翻译的页面，应明确说明缺少的内容和回退（fallback）到的语言。
- 保持指向现有根路径和已公开标题的链接。日语版是翻译源，放在现有路径上。
- 前提条件、运行示例、安全条件以及迁移和降级的限制，在各语言中保持一致。命令、标志、JSON 键、路径和产品标识符不翻译。
- 修改内容的 PR 也要更新相应的翻译。未翻译或待更新的内容要明确标注并跟踪，在有缺失的情况下不得标示为已支持所有语言。
- 由 CI 检查 3 种语言的链接、标题、语言间的对应关系以及翻译对象是否齐全。翻译的术语和技术准确性按语言分别评审。

本要求以文档为对象，不包括应用 UI 和 CLI 消息的翻译。

## 各语言的文件布局

| 日语（翻译源） | English | 简体中文 |
| --- | --- | --- |
| `README.md` / `CONTRIBUTING.md` | `README.en.md` / `CONTRIBUTING.en.md` | `README.zh-CN.md` / `CONTRIBUTING.zh-CN.md` |
| `docs/<path>`（索引、tutorials、guides、maintaining） | `docs/en/<path>` | `docs/zh-CN/<path>` |
| `docs/application-contract.md`（正本） | `docs/en/reference/application-contract.md`（概要） | `docs/zh-CN/reference/application-contract.md`（概要） |
| `GLOSSARY.md`（正本） | `docs/en/reference/glossary.md`（概要） | `docs/zh-CN/reference/glossary.md`（概要） |

契约和术语表的英文版与中文版是概要。它们链接到正本的对应章节，并注明如有出入以日语正本为准。术语同时标注正本中的日语写法。ADR、验证记录、过去的调查与评审、`AGENTS.md`、AI 代理（agent）工作流文档以及第三方许可证的核对不在翻译范围内。在翻译版的索引中，这些链接会注明原文的语言。

在每个页面的标题之后，以 `[简体中文](…) · [English](…) · 日本語` 的形式（此为日语页面的示例）放置语言链接，当前语言不做成链接。链接目标是内容相同的页面，不附加指向标题的片段（fragment）。无法提供翻译的页面，在 `scripts/check_docs.py` 的 `TRANSLATIONS` 中将该语言设为 `None`，并在其他语言版本中以 `[English → 日本語](…)` 的形式链接到日语版。如果翻译未跟上日语版的变更，则在标题和语言链接之后放置 `<!-- translation: stale -->`，以及用该语言写的 `> ` 提示。检查程序会分别显示已完成、待更新和回退的数量。

## 文件位置与信息归属

| 位置 | 读者与作用 | 更新时机 |
| --- | --- | --- |
| `README.md` | 初次访问者。目的、安装和接下来要读的页面 | 产品范围、安装入口或主要页面发生变化时 |
| `docs/README.md` | 寻找所需步骤的人。任务与文档的索引 | 页面被添加、移动或废弃时 |
| `docs/tutorials/` | 初次使用者。达成一个结果的有序步骤 | 初次操作发生变化时 |
| `docs/guides/` | 有明确目的的用户。反复进行的操作和问题处理 | 操作步骤或限制发生变化时 |
| `docs/application-contract.md` | 用户和自动化脚本的作者。公开接口的准确约定 | CLI、JSON、兼容性或分发要求发生变化时 |
| `GLOSSARY.md` / `docs/adr/` | 设计者。术语和决策的理由 | 术语或设计决策被添加或更新时 |
| `CONTRIBUTING.md` / `docs/maintaining/` | 贡献者和维护者。开发与发布 | 检查、评审或维护流程发生变化时 |
| `*.en.md` / `*.zh-CN.md` / `docs/en/` / `docs/zh-CN/` | 英文和中文读者。与日语版内容相同的翻译，以及契约和术语表的概要 | 对应的日语页面发生变化时 |
| `docs/verification.md` | 评审者和维护者。按时间点记录的验证证据 | 验证或发布审计完成时 |
| `.scratch/<feature>/` | 工作者。研究、规格、工单和工作记录 | 按功能进行调查和推进时 |

契约以 `application-contract.md` 为准，术语以术语表为准，发布规则以 `AGENTS.md` 为准。指南只给出完成操作所需的示例，不复制全部标志或模式。验证记录和过去的评审反映记录当时的信息，不能代替当前契约。

## 编写页面

- 在开头说明目的，并提供返回文档索引的链接。
- 教程中写明前提、操作所用的终端、需要替换的值、运行步骤、预期结果和后续操作。
- 指南中在需要的位置写明适用条件、操作、确认方法和恢复时的注意事项。
- 代码块要指定 `sh` / `powershell` 等语言。不要在命令中混入 shell 提示符。
- 示例要与实际存在的命令一致。如果固定版本只是演示指定方式的示例，请明确说明。
- 不要刊载私钥或认证信息。要区分生成与显示和运行、从管理中移除和吊销访问、构建和实机验证。
- 内部链接使用相对路径，移动页面时要检查现有的链接来源。已公开的标题尽可能保留指引。

## PR 检查

1. 确认可以从[索引](../README.md)进入新页面。
2. 运行 `python scripts/test_docs.py` 和 `python scripts/check_docs.py`，验证链接目标、标题、语言链接和翻译是否齐全。此检查不使用网络，不检查外部 URL 的响应或翻译质量。
3. 在 Markdown 预览中检查标题、表格、代码块和页面之间的导航。将命令示例与契约、`--help` 及受影响的测试进行核对。
4. 规范评审检查文件位置、语言、术语、信息归属和现有链接。规格评审则另行检查工单的完成条件，以及用户能否完成操作步骤。修改了翻译时，按语言将术语、命令示例、安全条件和兼容性约定与日语版进行核对。
5. 在 PR 中记录验证的 SHA、环境、结果和局限，不要把未验证的事项当作成功。

检查程序的对象是 README、CONTRIBUTING、术语表、AGENTS，以及索引、tutorials、guides、maintaining、ADR、AI 代理（agent）工作流文档、应用契约及其英文版和中文版。对于历史文档和 `.scratch/`，只检查链接目标是否存在，不会把旧内容递归改写为当前规格。添加新的文档组或需要翻译的页面时，也请更新 `scripts/check_docs.py` 的检查对象和 `TRANSLATIONS`。

仅修改文档时，作为普通的评审 PR 发布。应用的版本、标签和分发物按照[现有的发布流程](releases.md)处理。
