# ADR 0008: 署名付きフリート名簿で端末間の公開鍵を揃える

- 状態: 提案（未実装。採用後、フェーズ1から段階的に実装）
- 日付: 2026-11-28
- 仕様: `.scratch/fleet-sync/spec.md`
- 設計: `.scratch/fleet-sync/design.md`
- 更新（採用時）:
  - ADR 0001：リモート登録・解除とSSH config / Includeの所有・編集を外した判断
  - ADR 0004：自動のリモート失効を対象外とする境界
  - ADR 0007：鍵ペアのみの範囲、`authorized_keys` を利用者の手動配置に任せる
    方針、known_hosts・SSH configを編集しない方針

## 背景

ADR 0007は、ツールをこの端末の鍵ペアの管理に絞り、環境間で鍵を揃える仕組みを
後続の設計として別のADRで決めるとした。利用者は多数のPC・VM・VPSを使い、
接続先にはWindowsもある。接続先の多くで管理者権限を持ち、ログインには
主に同じアカウント名を使う。新しい環境での手作業は、ツールを取得する
1行のコマンドだけにしたい。インターネットを通すのは公開鍵だけとする。

公開鍵は秘密ではないため、守るべき性質は完全性と真正性である。転送中や
保存先で公開鍵を差し替えられると、偽の鍵でログインされるか、偽のホスト鍵で
中間者攻撃を受ける。すべての端末が一度だけ固定する信頼の起点が必要になる。

## 決定

署名付きのフリート名簿（Roster）を中心に、SSH KeyFlowを段階的に拡張する。

- **端末と役割**：フリートに参加した端末をノード（Node）と呼ぶ。役割は、
  SSHで接続する側の接続元（`client`）と、sshdで受ける側の接続先（`remote`）で、
  両方を持てる。OpenSSHの `Host`・ホスト鍵・`known_hosts` と衝突するため、
  接続元を「host」と呼ばない。
- **鍵**：秘密鍵は各ノードで作り、外に出さない。接続元はツールで鍵ペアを作り、
  接続先は既存のsshdホスト公開鍵を読むだけにする。
- **信頼の起点**：管理ノードが持つパスフレーズ付きEd25519のフリートルート鍵。
  各ノードは参加時にその公開鍵の指紋を確認して固定する。紛失に備えて
  オフラインの予備ルート鍵を登録でき、固定するのはこれらのルート公開鍵だけである。
- **名簿**：ノードのID・名前・役割・ログインアカウント・アドレス・接続元の
  公開鍵・接続先のホスト公開鍵を並べた、版番号付きの文書。既定では
  すべての接続元が、すべての接続先の共通アカウントへログインでき、
  接続先ごとに別のアカウントを指定できる。
  ネイティブの `ssh-keygen -Y sign` で名前空間 `ssh-keyflow-roster` の署名を
  付け、`ssh-keygen -Y verify` で検証する。署名が不正または未知のもの、
  既に見た版より古いもの、既に見た版と同じ番号で内容が異なるもの
  （ロールバック）は拒否し、設定した期間より古いもの（凍結攻撃）は警告する。
- **適用**：接続先では、ログインアカウントの `authorized_keys` の中のツール所有の
  区切りブロックだけを書き換え、ブロック外の行は変更しない。これは管理者権限を
  必要としない。Windowsの管理者アカウントは `%ProgramData%\ssh\administrators_authorized_keys`
  を使うため、書き換えには昇格が要る。接続元では
  アプリ所有のknown_hostsとSSH configを作り、`~/.ssh/config` から1回だけ
  Includeする。v0.10.0のガイドが残した `~/.ssh/ssh-keyflow/known_hosts` と
  `~/.ssh/ssh-keyflow/config` は引き継がず、別のファイル名を使う。
  適用は差分を示し、原子的に行い、`--dry-run` を持つ。
- **配布**：既定は自分で運用する信頼しない中継サーバー（Relay）とし、署名済みの
  名簿と参加時の合言葉交換の受け渡しだけを担う。中継サーバーは更新を
  止められるが、鍵を偽造できない。読み取り専用の静的配置（HTTPS・S3・git）と
  ファイル受け渡しも使える。
- **参加**：新しいノードは `join` で短い合言葉を表示し、管理ノードが `approve`
  する。両者はSPAKE2で相互認証し、新しいノードは公開鍵を送り、管理ノードは
  ルート公開鍵と中継サーバーのURLを返す。管理ノードは指紋と役割を示してから
  次の版に署名する。

このADRで決めるのは、署名付き名簿を中核にすることと、フェーズ1の範囲である。
配布と参加の方式（中継サーバー、SPAKE2）は現時点の方針で、各段階の仕様で
再確認し、変える場合は別のADRで記録する。

実装は単独で使える段階に分ける。

1. ノードID・役割・フリートルート鍵・名簿形式・署名と検証、ファイルでの受け渡し。
   SSHのファイルはまだ書き換えない。
2. `apply`：`authorized_keys` の管理ブロック、known_hosts、SSH configのInclude。
3. `join` / `approve` とSPAKE2による参加。
4. 中継サーバー、静的配置、定期的な `sync`。
5. 失効の操作、鍵の更新、予備ルート鍵、署名付きのインストーラー用チェックサム。

状態は名簿とノードの情報を持つためスキーマv4にし、v3からの移行はADR 0007と
同じく元のファイルを排他的に書き出してから行う。各段階のCLI・JSON・状態の変更は
リリース時にアプリケーション契約へ記録する。

## 検討した代案

- **Tailscale SSH / Headscale**：鍵管理そのものが不要になるが、SSHサーバー機能は
  LinuxとmacOS（オープンソース版CLI）だけで（tailscale.com/kb/1193、
  2026-11-28確認）、Windowsの接続先を扱えず、SSH鍵を第三者やIdPの
  識別に置き換える。
- **OpenSSH証明書を中核にする**：接続先の変更なしに接続元を追加できる。
  利用者は多くの接続先で管理者権限を持つため、`sshd_config` の
  `TrustedUserCAKeys` とKRLの `RevokedKeys` は設定できる。ただし、管理者権限の
  ない接続先では失効に短い有効期限とオンラインのCA鍵が必要になり、中核の
  方式が接続先ごとに変わる。名簿は権限の有無やOSによらず同じ方式で動き、
  署名鍵をオフラインに保てる。証明書は管理者権限のある接続先向けの
  追加モードとして後で検討し、同じ名簿で運ぶ。
- **GitHubの `<user>.keys`**：配布の基盤は不要だが、接続元の公開鍵しか扱えず、
  役割を持てず、信頼がGitHubアカウントの安全性に依存する。
- **P2Pのみ**：中継サーバーは不要だが、両端が同時にオンラインで、NAT越えが
  必要になる。止まっていることの多いVMやノートPCが追い付けない。

## 影響

- 0.x開発の機能追加として、各段階をMINORでリリースする。
- 攻撃面が広がる：中継サーバー、定期実行、署名鍵。フリートルート鍵が
  漏れるとフリート全体が影響を受けるため、パスフレーズ、予備鍵、
  更新手順、承認時の指紋表示で緩和する。
- `authorized_keys` の不具合は締め出しにつながるため、管理ブロックの外に
  緊急用の鍵を1本残すよう案内する。
- 接続先のみのノードにもsshdが必要で、Windowsでは導入に管理者権限が要る。
- ツールを動かせない端末（NAS・ルーター・制限されたサーバー）は、引き続き
  `keys public` の出力を手で配置する。
