# SSH KeyFlow — 最小実装計画

Status: ready-for-human
Released: v0.1.0（`ee3a00f`）。自動登録・解除はv0.5.0（`6a09684`、PR #8、ADR 0001）で廃止

仕様は spec.md、用語は ../../GLOSSARY.md を参照する。これは実装順と内部設計を示す計画であり、本体はまだ実装していない。

## 構成

```text
cmd/ssh-keyflow/main.go      起動と終了処理
internal/app/               対話、登録・解除の手順、進捗と結果
internal/state/             JSON、固定ID、バックアップ、排他、設定生成
internal/ssh/               コマンド実行、鍵操作、OS判定、登録・解除と手順生成
install.sh                  Linux/macOS用インストール・更新・削除
install.ps1                 Windows用インストール・更新・削除
.github/workflows/          検証とリリース
```

最初からプラグイン機構や汎用的な拡張層を作らない。OS別処理は internal/ssh 内に集める。外部コマンド実行は、実際の実行とテスト用の応答を切り替えられる小さな interface にする。JSON の検証には一時ディレクトリ上の実ファイルを使う。

## 実装上の既定値

- 本体の配置先：Linux/macOS は ~/.local/bin、Windows は %LOCALAPPDATA%\Programs\ssh-keyflow。
- PATH は現在の状態を確認して重複追加しない。永続設定の変更は対象と差分を表示して確認し、対応できないシェルには手動手順を表示する。
- インストール時は最新の正式リリースを既定とし、install.sh には --version、install.ps1 には -Version で版を指定する設計とする。
- リリースの配置先は実際の GitHub リポジトリが決まってから設定する。仮の配布先を動作済みとして扱わない。
- 鍵生成を始める前、またはリモート変更を始める前に、対象 ID・ファイルパス・実行段階を記録する。中断後に新しい鍵を不要に増やさない。
- JSON の形式が壊れている場合や未対応の version の場合、空の状態で上書きしない。
- ロックが残っている場合、使用中か不明なまま削除しない。状態と対処方法を案内する。
- パスフレーズ入力などで実際の端末が必要な操作は、端末が使えない場合に理由を案内して停止する。

## OS別の登録処理

### Linux / macOS

- 標準の登録先 ~/.ssh/authorized_keys を対象とする。
- 既存行、コメント、他の鍵を保持し、自分の指定した公開鍵だけを扱う。
- 新しく作るファイル・ディレクトリは必要な所有者権限にする。既存の権限に問題があれば、全体を無断で書き換えず修正手順を示す。
- サーバーが独自の登録先を使っているなど標準構成を確認できなければ、自動処理を止めて手動手順へ切り替える。
- macOS の SSH 有効化案内ではリモートログインとアクセス許可ユーザーを確認する。

### Windows

- 標準ユーザーと Administrators グループのユーザーを区別する。
- 標準構成での登録先はユーザーの .ssh/authorized_keys、管理者用は %ProgramData%\ssh\administrators_authorized_keys とする。
- 管理者用ファイルは共有範囲を持つため、パスと影響範囲を変更前に表示する。
- ローカライズされたグループ名に依存せず、SID を用いて権限を扱う。
- 必要な権限がない、独自構成がある、登録先を確定できない場合は、自動昇格せず手動手順を表示する。
- 既存 ACL に問題がある場合は、他の設定を無断でリセットせずに修正手順を示す。

### 共通

- OS・登録先が確認できるまで、変更用コマンドは実行しない。OS の確認だけに失敗した場合も選択を促す。
- 自動登録とコピペ用手順は同じ登録処理から生成し、動作の差を減らす。
- ユーザー入力をシェルのコードとして連結しない。鍵・アドレス・ユーザー名・パスを検証し、データとして扱う。
- 解除前の別認証確認は、解除対象の鍵や既存の多重化接続を使わず、新しい接続で実施する。
- 指定した鍵の接続確認を、別の鍵やパスワードで成功した結果と取り違えない。
- リモート変更後に応答が失われた場合は結果不明とし、読み取り確認後に再開する。

## 既存設定の保護

- 発見と明示的な取り込みを区別し、発見だけで管理対象にしない。
- Include を無条件にファイル末尾に追記しない。Host / Match の適用範囲と、先に得た値が優先される規則を考慮して、差分を表示する。
- 読み込みや解析を理由に既存設定の Match exec 等を無断実行しない。Include の循環や読み取り不可は注記する。
- 重複する別名やワイルドカード設定の影響を確認し、既存行の書き換えでは解決しない。
- 取り込んだ鍵ファイルの削除でも、対象パスと指紋を再確認する。ファイルの置き換わりや要確認状態があれば処理を止める。

## 実装順

1. main の初期設計コミットを基点に implement/ssh-keyflow で Go の最小構成を作る。implement-spec に従い、チケットごとに専用ブランチと作業ツリーで実装・統合する。環境チェック、対話メニュー、空状態の読み込みまでを通す。
2. JSON の安全な保存、既存鍵・接続設定の表示、鍵の作成・明示的な取り込みを実装する。
3. 接続先の登録、OS別の手動登録手順、進捗保存と再開を通す。
4. 自動登録、指定鍵での接続確認、専用 SSH 設定の生成と Include 追加確認を実装する。
5. 別認証による新規接続確認、登録解除、条件付きのローカル鍵削除を実装する。
6. インストール・更新・アンインストール、6種類のビルド、リリース手順を整える。

各段階で動く利用フローを完成させる。全層のひな形だけを先に大量に作らない。

## 検証

- 一時ディレクトリで鍵・JSON・設定を扱い、ユーザーの実際の ~/.ssh は検証で変更しない。
- 既存の管理対象外のファイル・設定が保持されることを、変更前後の内容で検証する。
- JSON 破損、書き込み失敗、変更処理の競合、中断後の再開を検証する。
- 同じ公開鍵の再登録、解除済み鍵の再解除で重複や意図しない削除が起きないことを検証する。
- パスに空白や日本語がある場合、公開鍵のコメントに記号がある場合を確認する。
- 引数と出力にパスワード・パスフレーズが残らないことを確認する。
- OS別の生成手順のテストと、実際の OS 上での接続検証を区別する。実機がなく未確認の範囲は報告する。
- 6種類のバイナリをビルドし、クロスビルド成功だけを実機動作確認と呼ばない。
- 実際の端末への登録・解除は、検証対象が指定された後に行う。
